# 学习路线与教学约定

- 建立日期：2026-11-16
- 仓库：`so5201314/algorithm-lab`
- 适用范围：C++ 算法训练、C 语言编程训练、偶尔穿插的数学思维训练
- 状态：长期执行、根据实际表现迭代，不设必须按周完成的刚性期限

## 1. 总目标

本仓库服务于嵌入式工程师的长期能力成长，不以竞赛排名或刷题数量为目标。

最终希望形成四种能力：

1. **问题分析**：读懂需求、输入输出、约束和边界，能把问题拆成步骤。
2. **独立编码**：能用 C 写出可靠的小模块，能用 C++ 表达和验证常见算法。
3. **工程判断**：知道什么时候需要数据结构或算法，能在时间、RAM、Flash、实时性和可维护性之间取舍。
4. **验证与复盘**：能设计测试、定位错误、解释实现，并判断 AI 给出的方案是否可信。

刷题是训练手段，不是最终目的。学习内容应尽量迁移到 GPIO、UART、SPI、I2C、ADC、FreeRTOS、端口管理、协议解析和电源状态机等嵌入式场景。

## 2. 三条训练主线

### 2.1 C 语言基础与工程编码（Dotcpp，优先级最高）

目的：恢复并建立独立编写 C 程序的能力，为 MCU 固件开发打基础。

建议路线：

| 顺序 | 模块 | 重点能力 | 典型工程联系 |
| --- | --- | --- | --- |
| 1 | 数组 | 遍历、查找、插入、删除、元素移动、二维数组 | 端口表、采样数据、固定容量缓冲区 |
| 2 | 字符数组与字符串 | 结束符、长度、比较、复制、解析 | UART 命令和文本协议处理 |
| 3 | 函数 | 参数、返回值、作用域、拆分模块 | 驱动接口和业务函数 |
| 4 | 指针 | 地址、解引用、数组与指针、指针传参、const | 缓冲区、驱动 API、数据共享 |
| 5 | 结构体与枚举 | 数据组织、结构体数组、结构体指针、状态表达 | `port_info_t`、设备配置、状态机 |
| 6 | 内存与生命周期 | 全局/静态/栈/堆、数组容量、越界、动态内存基本原理 | MCU RAM 规划和生命周期管理 |
| 7 | 位运算 | 与或非异或、移位、掩码、置位/清位/读取位 | GPIO、寄存器、状态标志 |
| 8 | 常用数据结构 | 栈、队列、链表、环形缓冲区；理解哈希表的适用场景 | 事件队列、UART 接收、设备管理 |
| 9 | 常用算法 | 查找、排序、去重、计数、简单滤波 | 数据处理和配置查找 |

教学要求：

- Dotcpp 由教师（ChatGPT）筛选具体题目，用户不必在混合语言题库中自行找题。
- 进入题目后选择 C 语言；不因网站同时支持 C++、Java、Python 就随意切换。
- 一次聚焦一个主要知识点，必要时用一题变体巩固。
- 先理解数组容量与有效元素数量的区别，再进入更复杂的指针和内存操作。
- 动态内存要理解，但在 MCU 场景中不默认鼓励使用堆；是否使用取决于芯片资源和项目约束。

### 2.2 C++ 算法与数据结构（LeetCode）

目的：训练算法思维、数据结构选择、复杂度分析和问题建模。C++ 是算法学习工具，不代表要求用户把工作中的 C 固件改写成 C++。

已接触的主题：

- 数组、哈希表、集合与计数。
- 双指针、滑动窗口。
- 前缀和与哈希计数。
- 单调队列。
- 排序、比较次数和锦标赛式算法。

后续主题按掌握情况逐步推进：

1. 完成和复习当前滑动窗口题目，特别是可变长度窗口（如 LeetCode 76）与固定窗口、单调队列的区别。
2. 回顾前缀和 + 哈希表（如 LeetCode 560），确保能独立写出查询顺序和计数逻辑。
3. 二分查找、栈与队列、链表。
4. 树的遍历、递归、BFS/DFS。
5. 堆、优先队列、贪心。
6. 动态规划和图算法：在基础稳固后按需要选择，不为覆盖题型而机械刷题。

选题原则：

- 每道题说明它训练什么、为什么选它、前置知识是什么。
- 同一知识点先做代表题，再做一题变体；不连续堆叠大量相似题。
- 重点解释“为什么选择这个数据结构”，而不只是讲代码如何运行。
- 对复杂度分析保持工程化：同时看时间、辅助空间、输入规模和常数成本。

### 2.3 数学思维（偶尔穿插，不设硬性题量）

目的：保持数学直觉，训练抽象、推理和证明能力，辅助理解算法与工程原理。

可选主题：

- 逻辑、集合、奇偶性、计数。
- 不变量、反证法、必要条件与充分条件。
- 组合数学和图论入门。
- 线性代数、微积分、概率统计中的基础概念。

教学方式：

- 通常一次一道短题，不把数学变成额外的打卡负担。
- 先让用户判断和解释，再给提示；不急着公布证明。
- 区分“找到了一个例子”“满足必要条件”和“证明了充分性”。
- 尽量连接算法、滤波、采样、误差、概率等工程场景。
- 当用户提出“来道数学题”时，可以独立安排一题；若当前编码训练有明显薄弱点，也可选择相关数学题帮助理解。

## 3. 学习节奏

建议参考节奏，而不是硬性 KPI：

- 每周约 2～3 次短学习，每次约 30～45 分钟；工作忙时可以减少，不通过熬夜补进度。
- C 语言训练是当前主线；LeetCode 与 Dotcpp 交替安排，避免同一晚塞入多个新概念。
- 数学题偶尔穿插，不要求每周必须完成固定数量。
- 每次只推进 2～4 个小步骤，保留时间用于自己写、运行和思考。
- 每隔若干次练习做一次复盘，根据错误类型调整后续选题。

## 4. 单题教学流程

默认采用以下流程：

1. **选题与目标**：说明题目训练点、前置知识、输入输出和约束。
2. **用户先思考**：先让用户口述思路、变量含义或边界情况，不立即给完整答案。
3. **分层提示**：先给一个关键问题；仍卡住时再给局部提示、伪代码或最小代码片段。
4. **用户编码**：用户自己输入代码；允许先写不完整版本，再逐步修正。
5. **检查与验证**：区分语法/编译错误、逻辑错误、边界错误、复杂度问题；使用样例和反例测试。
6. **解释原理**：先解释变量、条件和模块职责，再串联主流程；不重要细节不过度展开。
7. **工程迁移**：说明该知识在 MCU 中是否常用、何时值得使用、资源和实时性方面有哪些取舍。
8. **记录掌握度**：更新进度文档和学习日志，并决定复习、变式练习或进入下一主题。

### 提示等级

- H0：只提出问题，引导用户独立推导。
- H1：给方向性提示，不给代码。
- H2：给伪代码或关键表达式。
- H3：给最小可运行片段，并解释关键机制。
- H4：在用户明确需要、或多轮引导仍无法推进时，提供完整参考实现，再要求用户复述和修改。

默认不跳过用户思考直接给完整答案。若用户明确要求完整代码，可以提供，但仍要解释关键部分并安排理解检查。

## 5. 代码 Review 与验证标准

每道题按实际相关性检查：

- 输入输出和题意是否理解正确。
- 下标、长度、边界条件是否正确。
- 是否有越界、未初始化、空容器访问、整数溢出等风险。
- 数据结构是否必要，是否存在过度设计。
- 时间复杂度和辅助空间是否符合约束。
- 函数职责、变量命名和代码可读性。
- 是否有足够测试覆盖正常、边界和异常输入。

验证状态必须明确区分：

| 状态 | 含义 |
| --- | --- |
| 思路完成 | 能说明算法，但尚未完整编码 |
| 代码完成 | 已写出代码，尚未验证 |
| 编译通过 | 编译器通过，不代表逻辑完全正确 |
| 测试通过 | 已通过记录的测试用例 |
| 在线提交通过 | 对应平台明确 Accepted |
| 实机验证通过 | 在目标硬件上完成验证 |

不得把 AI Review 通过、代码看起来正确或本地编译通过，写成在线提交或实机验证通过。

## 6. AI 协作原则

AI 是教练、结对编程伙伴和审查工具，不是替代用户理解的答案机器。

在刷题训练中：

- 先由用户尝试，AI 根据卡点提供分层提示。
- AI 可以解释 API、生成测试、检查边界和复杂度。
- AI 给出的代码需要阅读、运行、测试；不能因“AI 说没问题”就认定正确。
- 对关键题目，用户应能不看答案重新写出核心逻辑，并解释数据结构选择。

在真实嵌入式项目中：

- AI 可以承担更多代码生成、重构建议、测试设计和 Review 工作。
- 用户需要明确需求、硬件约束、接口和验收标准。
- 对中断、DMA、并发、时序、内存和保护逻辑，必须结合工程证据与目标板验证。
- 保留“计划 / 已编写 / 编译通过 / 测试通过 / 实机通过”的证据区分。

## 7. 掌握度评估

每个知识点或题目使用以下等级：

| 等级 | 判定 |
| --- | --- |
| A：独立掌握 | 不看答案可独立实现，能解释原理、边界和复杂度 |
| B：基本掌握 | 少量提示后完成，能解释主要逻辑；需要之后复写 |
| C：引导完成 | 需要分步骤提示，能跟上但尚不能独立实现 |
| D：尚未掌握 | 主要依赖参考答案，或关键原理仍不理解 |

“平台通过”与“掌握等级”是两件事：提交通过但无法解释，仍不能评为 A。

复习方式：

- 下一次学习开始时，简短回忆上次的核心规则。
- 对 B/C/D 知识点安排隔次复写或小变体。
- 如果同一错误重复出现，暂停增加新题，先安排针对性练习。
- 已达到 A 的内容可以降低复习频率，但在真实项目遇到时仍要重新核对上下文。

## 8. 动态迭代机制

课程不是固定不变的题单。每次练习后观察：

- 哪些概念理解了，但代码写不出来？
- 哪些代码能写出来，但解释不清楚？
- 错误主要来自下标、指针、类型、内存、循环边界，还是算法建模？
- 是否把某种数据结构用错场景，或为了复杂度而过度设计？
- 哪些知识已经能迁移到 MCU，哪些还停留在刷题层面？

调整规则：

1. **重复犯错**：增加一个更小的专项练习，不直接跳到更难题。
2. **能跟着写但不能独立写**：安排隔次复写和参数变化题。
3. **独立完成且解释清楚**：推进下一知识点。
4. **题目明显超出前置知识**：拆成前置小练习，不用完整答案硬推。
5. **工程中出现真实需求**：可以临时调整顺序，优先学习当前模块真正需要的知识。

每完成约 4～6 次训练，回顾一次路线和掌握情况；不为了遵守原计划而牺牲理解质量。
